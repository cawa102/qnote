# FindFileScreen border height 崩れ: 解決策提案

作成日: 2026-03-01  
対象: `src/tui/screens/FindFileScreen.tsx` / `src/tui/screens/SearchScreen.tsx`  
前提: **この文書は提案のみ。コード変更は未実施。**

## 1. 結論（推奨方針）

`height={3}` の固定指定をやめ、入力ボックスの高さを **自然高（content + border）** に任せる。  
同時に、ボーダー直下のステータス行を常時1行確保して、初回描画と非同期完了後でレイアウト木の形を変えない。

要点:
- `Box(borderStyle="bold")` に対して `height` を指定しない
- ステータス行は常時描画（空時は空文字/スペース）
- `scanNoteFiles` 完了時の状態更新は1回レンダリングに集約（`setState` 一括）

この3点で、FindFile固有の「初回+非同期更新」時の差分描画揺れを抑制できる。

## 2. なぜこの方針か

既存レポートで以下は既に否定済み:
- ラベル長
- margin
- 単純な折り返し
- TextInput単体のplaceholder描画

一方、FindFileだけが持つ差分は次の2つ:
- 非同期ロード完了で再レンダリングが必ず入る
- ボーダー直下の行が常時存在し、内容が変化する

`height=3` は「ボーダー2行 + 中身1行」でちょうど境界条件になり、差分更新が不安定な環境だと崩れが顕在化しやすい。  
自然高に戻し、下段1行も固定化すると、描画差分の形状変化が最小化される。

## 3. 具体的な解決案

### A. ボーダー行の高さ指定を撤廃（第一優先）

- FindFileの入力ボーダー `height={...}` を削除
- Searchも同じポリシーに統一（回帰防止）

期待効果:
- `height=3` 境界条件依存を回避
- 空状態の「余分な1行」問題を同時に解消

### B. ステータス行を常時1行確保（第二優先）

- `{fileCount}` 行を常時表示し、空時は空文字にする
- Search側も同様に、ヒント行を常時1行に固定する案が有効

期待効果:
- 条件分岐による縦方向の行数変化を抑制
- Ink差分描画時の相対位置ズレを低減

### C. 非同期完了時の state 更新を1回に集約（第三優先）

- `allFiles` と `isLoading` の更新を分離しない
- reducer かオブジェクトstateで1回コミット

期待効果:
- 連続フレームでの微妙な中間状態（空データ+loading false等）を減らす

## 4. 実装時の変更最小セット（提案）

1. FindFileのボーダー `height` 指定削除
2. FindFileのステータス行を1行固定化
3. Searchも同じレイアウト方針に合わせる
4. FindFileの非同期完了状態更新を一括化

備考: 1,2 だけでも症状が解消する可能性が高い。3,4 は再発防止の保険。

## 5. 検証計画（端末実機）

優先順:
1. iTerm2 / Terminal.app で `qnote` → FindFile初回表示
2. クエリ空/入力中/削除後 でボーダー崩れが出ないこと
3. 連続遷移（palette ↔ findFile ↔ search）を20回程度
4. 端末幅 80/100/120 で再確認

受け入れ基準:
- 上下ボーダーが欠けない
- 上ボーダーとコンテンツ行がマージしない
- 空状態でも余分な空行が発生しない
- Search/FindFileで見た目ルールが一致する

## 6. 代替案（非推奨）

- `height={query === '' ? 4 : 3}` の継続
  - 症状は回避できるが、空状態で冗長な1行が残る
- `margin/padding` の微調整のみ
  - 根本要因（差分描画の境界条件）に効きにくい

## 7. リスク

- `@inkjs/ui` / `ink` バージョン差で挙動が変わる可能性
- フォントやterminal描画実装差（Nerd Font, iTerm2設定）で再現率が変動

対策:
- `height` 依存を避ける設計にして、端末差分への耐性を上げる
- 将来的に `ink` アップデート時にこのケースを回帰テストへ追加
