# Command Palette レイアウト改善 提案書

作成日: 2026-03-01  
対象: `src/tui/screens/CommandPalette.tsx`（実装変更は本提案では未実施）

## 1. 背景と目的

現在のパレット行は、`Text` を横並びにしているため以下が起きやすい。

- 左側（`○/● + label`）と右側（`description`）の列境界が固定されない
- label 長に応じて description の開始位置がズレる
- 全体を中央に置きつつ、列ごとの左/右揃えを両立しづらい

目標は LazyVim 風に、以下を同時に満たすこと。

- 行ブロック全体は画面中央に見える
- 左列: 選択丸 + label を左揃え
- 右列: description を右揃え
- 短い端末幅でも破綻しにくい

## 2. 現状整理（実装観点）

- `CenteredLayout` が `contentWidth` 全体を中央寄せしている
- `CommandPalette` は `formatRuler(contentWidth)` を full width で描画
- 各コマンド行は `<Box><Text>左</Text><Text>右</Text></Box>` で、列幅の概念がない

このため「中央寄せされたコンテンツの中で、さらに“固定幅の2カラム行ブロック”を中央配置する」レイヤが不足している。

## 3. 提案アプローチ（推奨）

### A. 「行ブロック幅」を導入し、2カラム化する（推奨）

方針:

1. パレット行群専用の `menuWidth` を計算する  
2. 行コンテナを `width={menuWidth}` で中央配置する  
3. 各行を「左列固定幅 + 右列可変」に分割する  
4. 右列は `align="right"` で右寄せ表示する  

イメージ（概念）:

- 外側: `contentWidth`（既存の中央寄せ領域）
- 内側: `menuWidth`（例: 56〜72、または `contentWidth` に応じて可変）
- 行:  
  - 左列 `leftColWidth`（例: 26〜34）に `● label` を左揃え  
  - 右列は残り幅に `description` を右揃え

効果:

- label の長さに影響されず description の右端位置が揃う
- 行全体の塊が中央にあるため、視覚的に LazyVim 風の安定したレイアウトになる

## 4. 幅計算ルール（提案）

初期はシンプルな固定+クランプが安全。

- `menuWidth = clamp(contentWidth - 8, 44, 72)`
- `leftColWidth = clamp(floor(menuWidth * 0.62), 24, 38)`
- `rightColWidth = menuWidth - leftColWidth`

補足:

- `contentWidth` が狭い場合は `menuWidth` を自然に縮める
- 右列が極端に狭いときは description を省略表示（後述）

## 5. 狭幅端末へのフォールバック

狭いターミナルでは見切れ/折返しが起きやすい。段階的フォールバックを推奨。

1. `contentWidth < 50`:
   - description を非表示
   - 左列のみで操作性を維持
2. `50 <= contentWidth < 64`:
   - description を短縮（`…`）
3. `contentWidth >= 64`:
   - 通常の2カラム表示

これにより、可読性と操作性を優先しつつ「広い画面では理想配置」を実現できる。

## 6. 実装ステップ案（小さく導入）

1. レイアウト計算関数を `CommandPalette` 内に追加  
2. 行群のラッパー Box を `menuWidth` で中央配置  
3. 各行を2カラム化（左固定・右右揃え）  
4. 狭幅時フォールバック導入  
5. スナップショットテスト更新（`test/tui/command-palette*.test.ts`）  

## 7. テスト観点（受け入れ基準）

- 80x24 相当:
  - 行群が中央に配置される
  - 右列 description の右端が縦に揃う
- 120x30 相当:
  - 余白が増えても行群が間延びせず、中央に塊として残る
- 56x20 相当:
  - フォールバックが発動し、表示崩れなく操作可能
- 選択移動（上下キー）:
  - `●/○` の切替が維持され、列揃えが崩れない

## 8. 代替案（非推奨）

### B. `padEnd` で文字列整形して1つの `Text` に詰める

問題:

- ANSIカラー文字列や全角幅（CJK）で `length` ベース整形が崩れやすい
- 将来的な i18n/文言変更でズレが再発しやすい

### C. 完全固定ピクセル的な幅運用

問題:

- 端末幅差分に弱く、狭幅で破綻しやすい
- レスポンシブ性が低い

## 9. リスクと対策

- リスク: Ink の Text 折返しで予期せぬ2行化  
  - 対策: 狭幅時は description を非表示/省略に切替
- リスク: 文字幅（全角・記号）で視覚ズレ  
  - 対策: 幅計算は Box レベルで行い、文字列パディング依存を避ける
- リスク: タイトル/罫線との相対位置バランス  
  - 対策: `menuWidth` と `marginTop` を独立調整可能にする

## 10. 結論

最も堅実なのは「中央領域の中に、中央配置された固定幅メニューブロックを置く」2段レイアウト。  
この構成なら、要件である

- 左列の左揃え
- 右列の右揃え
- 全体の中央配置

を同時に満たし、端末幅の揺れにも対応しやすい。
